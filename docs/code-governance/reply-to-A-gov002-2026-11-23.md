# Reply to Member A: proposed revision of GOV-002

From: Member E.  
To: Member A.

This reply proposes changing the requirement. It does not claim that the existing implementation satisfies the current requirement for human approval of a test plan before implementation. Please record the revised wording and obtain the required team/course agreement before treating it as adopted. If prior test approval is mandatory under the course rules, this proposal needs to be reconciled with that obligation.

Q1: **Q1-a — file in the repository.** The evidence should be included in the submitted repository. For example, use `docs/verification/approvals/<feature>.yaml`. Where a feature has multiple PRs or runs, use a unique name such as `<feature>-pr-<number>-run-<run-id>.yaml` so that earlier evidence is preserved.

I will implement automatic receipt generation after the required PR checks finish, with successful PR receipts automatically archived in the repository as part of the merge/delivery process. Receipt generation and repository archiving are planned work; the current four CI gate categories do not yet implement them. A receipt generated by CI is a **verification record**, not a human test-plan approval.

Q2: **Please remove the separate request for human approval of a test plan before implementation and revise GOV-002 to cover CI verification and evidence retention before merging.** The intended workflow is:

1. A member writes the code and submits a PR targeting `main`.
2. CI/CD automatically runs the required checks.
3. CI/CD automatically generates a receipt recording the checked revision, check times and pass/fail results. Failed checks produce failure evidence and prevent merging; successful checks produce a success receipt. Receipts are retained and successful PR receipts are archived in the repository for delivery.

Existing repository rules for human PR review, if configured, still apply. There is no additional, separate test-plan approval request in this proposal.

**Suggested requirement wording for A to review and adopt:**

- **ID:** `REQ-TA-GOV-002` (proposed replacement; A owns the final registry entry).
- **Category:** Governance / development process.
- **Priority:** Must, subject to team adoption.
- **Statement:** For every implementation pull request targeting `main`, the repository shall prevent merging unless all required CI checks have succeeded for the current PR revision and a machine-readable verification receipt has been generated and retained for that revision. The automation shall archive the receipt for each successfully merged PR in the repository for final delivery. Separate human approval of a test plan before implementation is not required by this revised requirement.
- **Required checks:** `required tests`, `ruff (strict, full repo)`, `dependency check`, and `ai-log updated`. Each check applies its defined rules; for example, the AI-log gate requires an update only when critical paths change.
- **Receipt contents:** Repository identifier, PR number, PR head SHA, tested SHA (including the test merge SHA when applicable), workflow run ID/URL and attempt, check start/completion times with timezone, required-check names and individual results, and overall verification result. If a human PR review is included, record its actual reviewer and review reference separately; do not identify the CI bot as a human approver.
- **Fit criterion 1:** Given a PR targeting `main`, when any required check fails, is cancelled or skipped, or has no result, merging shall be blocked.
- **Fit criterion 2:** Given a PR whose required checks succeed, when CI finishes, a receipt shall exist and identify the exact revision and workflow attempt checked. Missing or mismatched evidence shall not satisfy the merge condition. A later change to the PR requires a new applicable check result and receipt.
- **Fit criterion 3:** Given a successfully merged PR, when the receipt-archiving automation completes, its receipt shall be present at the agreed repository evidence path. An archive failure shall be reported as a failed archive job and remain unresolved until the receipt is stored; it shall not be silently reported as complete. Before final delivery, every PR covered by this policy shall have its receipt in the submitted repository.
- **Verification:** Use passing, failing, cancelled/skipped, missing-receipt and stale-revision PR cases, plus a successful merge/archive case and an archive-failure case. Confirm both merge blocking and the receipt fields/files.
- **Status:** Proposed change only. Do not mark it implemented until receipt generation, receipt validation and repository archiving are implemented and verified.

The receipt must be generated and retained before merge eligibility is established; repository archiving may occur after merge. This separates the pre-merge verification decision from packaging the evidence into the final repository. The policy applies prospectively after adoption; historical work must not receive fabricated prior approvals.

The former Q2 fields `approver`, `approver_role`, `approved_at`, `plan_ref`, `plan_sha256` and `scope` describe human approval of a test plan. They should not be filled with invented values merely to make an automated CI receipt look like that approval. Please replace the mandatory field set with the CI receipt fields above for the revised requirement.

Q3: **Neither ancestry nor author/committer dates will be used to enforce prior test-plan approval, because that step is removed in the proposed process.** Commit ordering does not prove when coding actually began, and timestamp fields can be manipulated. The revised gate will verify that CI results and the receipt match the revision being merged. It will not claim to prove that implementation started after approval.

Q4: **No exception path is proposed.** Approver unavailability is not expected to occur in this team's working arrangement, so no separate absence or hotfix exception mechanism is requested. Under the revised process, single-member work and hotfixes follow the same required CI and receipt rules. Any human review required by repository policy still applies.
