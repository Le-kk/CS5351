To close the earlier questions about the mechanism, I propose the following implementation rules:

- **Storage — Q1-a:** Store an attributable approval record in `docs/verification/approvals/<feature>.yaml`. Use unique names where multiple approvals or revisions exist, and preserve superseded evidence. The evidence needed for assessment must be included in the submitted repository, not only available through a live GitHub link.
- **Minimum fields — Q2:** Record `approver`, `approver_role`, `approved_at` with timezone, `plan_ref`, `plan_sha256` and `scope` (the covered requirement/feature IDs). Add an `approval_evidence_ref` identifying the actual human confirmation and its retained evidence, and an `approval_commit` identifying the repository revision that contains the approved plan and record. The GitHub account, if used, should be mapped to the named team member. A bot-generated file is not itself human approval.
- **Approval method:** C prepares the relevant tests/test plan and the agreed human reviewer approves its specified scope before implementation starts. A separate test-plan PR is not mandatory under this proposal: an explicit team confirmation may be used if the named approver, approved version, scope and original confirmation are retained and verifiable. E records/integrates the evidence; automation must not manufacture the approval.
- **Ordering — Q3:** Use an approval revision that precedes implementation in the Git history, backed by the actual human confirmation. CI should verify that this approval revision is an ancestor of the first implementation commit for the declared scope, rather than accepting a self-entered timestamp as sufficient proof. Where available, retain GitHub's review/submission timestamp and reviewed commit as additional evidence. Ancestry supports the repository ordering check; it does not independently prove when coding began or that a human genuinely approved the tests. The requirement and evidence must not claim that it does.
- **Version and scope binding:** Validate the plan hash against the plan at the approved revision and check that the approval covers the implementation scope. Do not silently apply an approval to a materially changed test plan or an additional feature. Changes to the approved test scope require renewed approval before the corresponding implementation work.
- **Blocking behavior:** An implementation PR must fail its approval check if the required record is absent, incomplete, does not identify retained human evidence, refers to the wrong plan revision/scope, or cannot establish the required pre-implementation ordering. A later successful test run or a CI verification receipt cannot substitute for the missing prior approval.
- **Exceptions — Q4:** No hotfix, single-member or approver-absence exception is proposed. The same approval rule applies. Historical work without sufficient evidence must be disclosed as an evidence gap; do not backdate approvals or describe retrospective review as prior approval. Any alternative treatment needs an explicit course-authorized decision.
- **Verification before completion:** Demonstrate an accepted PR with valid prior approval and rejected cases for missing approval, approval recorded after implementation, mismatched plan hash/scope and an unsupported approval claim. C should review the test coverage. Until then, record this gate as pending implementation/verification.

These are the intended rules for integration, not a claim that a tamper-proof proof of real-world development timing is possible. C and E will define the implementation-path/scope mapping explicitly so that the first implementation commit is identified consistently. Automatic CI receipts remain useful supplementary evidence of checks against a revision, but they are separate from this human approval record.
