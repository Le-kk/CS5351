# 三个共同盲区的解决方案

先说明一个贯穿三案的共同前提：**这三个盲区都不是"文档没写清"，而是"要求的强度超过了当前架构能保证的范围"**。所以方案的核心不是补措辞，而是**把不可保证的承诺换成可检验的弱承诺 + 一个显式的"未达标"状态**。

---

## 盲区 1：并发预算的可执行性

### 问题在哪（项目里的实际证据）

`graph/setup.py` 确认分析师是**真并行**的（`START → 4 个 analyst + Memory Log`）。所以：

- 4 个分支会**同时**发起调用，`if counter < cap` 这种检查必然超发
- `factory.py` 把 `max_retries` **透传给 SDK**，SDK 内部的隐式重试**应用层看不见、拦不住**
- `_NOT_IN_SIGNATURE` 明确把 `llm_max_retries` 排除在签名外，说明 retries 不影响"运行产出"——但它**影响花费**，这个排除和预算语义是打架的

结论：**"run-wide 硬上限"在 SDK 隐式重试存在时，应用层最多做到"近似上限"**。

### 方案 A（推荐）：预留式预算 + 明示的透支上界

不是"计数到 8 就停"，而是**分发前原子预留**：

```
reserve(n=1):
    with lock:
        if reserved + 1 > CAP: raise BudgetExhausted
        reserved += 1          # 预留，不是消费
    dispatch()
    on success: reserved -= 1; consumed += 1
    on failure: reserved -= 1  # 只回滚应用层可见的失败
```

关键设计：

1. **硬关闭 SDK 重试**（`max_retries=0`），把重试上移到应用层。这是唯一能让"应用层计数 = 真实调用数"的方法。
2. **定义`最大透支 = 并发分支数`**：如果 4 个分支在预留的瞬间同时通过，最坏超发 4 次。把这个写成**显式上界**，而不是假装精确。
3. **验收标准改成可检验的弱形式**：
   - 不是 "调用数 ≤ 8"
   - 而是 "**调用数 ≤ 8 + 并发分支数，且 0 次发生在预留之外**"

### 方案 B（若不愿关 SDK 重试）：计费式而非拦截式

做不到"不超过"，就改成"**发现并披露超支**"：记录实际调用，超支时标 `BUDGET_EXCEEDED`，并**降级为 Should**。这是诚实的退让，但优先级必须改。

### 对本项目的具体建议

- 保留 COST-002 为 **Must**，但把语句从"enforce a cap"改为"**bound and detect**"
- 验收：`dispatch_count ≤ CAP + N_branches`，且 `0` 次未经预留
- 加一个**并发竞态 fixture**：4 个分支同时抢最后 1 个额度，断言只放行 1 个

# 两者的分别

## 一句话

- **保证强度声明** = “我保证到什么程度”（需求问题）
- **必须关 SDK 重试** = “用什么技术手段达成”（设计/实现问题）

打个比方：你投票表决的是“这栋楼要能抗 8 级地震”，不是“必须用某种型号的钢筋”。前者是你的权限，后者是结构工程师的权限。

---

## 具体到 COST-002

### 写法 A：保证强度声明

> **Statement**：系统应保证单次运行的 LLM 调用次数有上界 `CALL_CAP + N_concurrent_branches`，且每次 provider 分发都必须先取得一个已计入预算的预留；本上界以外的调用不得占用预算。
>
> **Fit criterion**：(a) 100% 的 dispatch 前有成功预留；(b) 总数 ≤ 12；(c) 4 分支抢最后 1 个额度只放行 1 个；(d) 结束为 `INCOMPLETE(BUDGET)`。

**它说了什么**：保证一个可证明的上界，以及“预留先于分发”这个**可观察的行为**。
**它没说什么**：不指定预留怎么实现、不指定是否关 SDK 重试。

### 写法 B：必须关 SDK 重试

> **Statement**：应用层必须调用 SDK 时设置 `max_retries=0`，所有重试由应用层自行实现并计入预算。

**它说了什么**：指名一个具体的 API 参数。
**问题**：这是 `llm_clients/factory.py` 的实现决定。如果 B 后来决定“我们用带计数的 wrapper 不加 `max_retries=0`”，这条需求就把一个合法的设计判成不合规。

---

## 关键：为什么写法 A 不会被绕过

很多人担心“只说保证强度，实现的人可以敷衍”。不会，因为**验收标准还是硬的**：

| | 写法 A 能拦住什么 |
|---|---|
| 应用层不计数 | (a) 失败——没有预留就没有 dispatch |
| SDK 偷偷重试 | (b) 失败——一旦超发，总数超过 `CAP + N` |
| 检查用 `if n < cap` 而非预留 | (c) 失败——4 分支会都通过 |
| 超支不报告 | (d) 失败——不是 `INCOMPLETE(BUDGET)` |

**写法 A 的验收标准恰好把所有已知的作弊路径都堵住了**，而且**不要求它必须用某个特定的手段**。这正是“可检验的弱承诺”优于“不可检验的强承诺”的地方。

---

## 那“关 SDK 重试”去哪了？

它变成 **D 的一个实现选项**，记在 D-4 里：

| 如何让应用层计数 = 真实调用数（如设置 `max_retries=0`） | B（设计）、D（实现） | 建议，非强制 |
